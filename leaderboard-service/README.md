# TetrisGame leaderboard service

Cloudflare Workers + D1 backend for the QGIS plugin. GPL-3.0-or-later, as in the repository's LICENSE.

Production URL: `https://tetrisgame-leaderboard.gaojunke2020.workers.dev`

## Develop and verify

Requires a current Node.js version supported by Wrangler. Run `npm ci`, `npm run typecheck`, and `npm test` in this directory. Tests use the actual local workerd/D1 runtime and only disposable local data. The latest published workerd used here supports 2026-09-03; local dev/tests explicitly use that date, while production uses 2026-09-05. The Miniflare v5 compatibility adapter is used for the documented v4-style test configuration. All development dependencies are locked in package-lock.json; none ship inside the QGIS ZIP or run in the deployed Worker.

`npm run dev` uses a local HTTPS development certificate. Do not bypass certificate validation in the shipped plugin. Use the isolated API tests for local integration, or a trusted HTTPS test deployment for QGIS network tests.

## Deploy / maintain

1. Authenticate using `npx wrangler login`. If the localhost callback fails, use `npx wrangler login --device`.
2. For a new account, create a dedicated database with `npx wrangler d1 create tetrisgame-leaderboard` and update the public database ID in wrangler.jsonc. The current database already exists: do not recreate it on updates.
3. Apply pending migrations with `npx wrangler d1 migrations apply tetrisgame-leaderboard --remote`.
4. Run `npm run typecheck`, `npm test`, then `npm run deploy`.
5. Verify `GET /health` and `GET /v1/leaderboard` over HTTPS. Update the plugin's `leaderboard_config.py` only if the public service address changed.

The deployment adds no custom-domain route, alters no existing DNS, and requires no shared secret in the plugin. Database/account IDs are configuration, not authorization credentials. OAuth credentials stay in the local Wrangler credential store. Never commit `.dev.vars`, `.env`, `.wrangler`, tokens, or local settings.

This setup does not request a paid plan upgrade. Cloudflare's account plan and current usage limits apply; review the dashboard as traffic grows. Retain/export the D1 database before schema changes. The initial schema is append-only and preserves every accepted event for idempotency; online records do not expire automatically.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/health` | Service/database health |
| GET | `/v1/leaderboard` | Public top five, only nickname/score/country |
| POST | `/v1/player` | Get/create anonymous profile; body `{}` |
| POST | `/v1/scores` | Submit a completed/ended round |
| DELETE | `/v1/player` | Delete own profile and associated events |

Authenticated calls use `Authorization: Bearer <43-character base64url installation token>` generated by Python `secrets.token_urlsafe(32)`. The server stores only a SHA-256 digest. The nickname is deterministically generated from a separate digest. There is no password, login, country selector or nickname input.

Score JSON: `event_id` (32 lowercase hex characters), integer `score`, `lines`, `pieces`, `duration_ms`. Bodies are bounded at 2 KiB. Country is read exclusively from `request.cf.country`; a submitted country/nickname is rejected. The best-score country is the country of the connection when that result was received, not necessarily when an offline game was played.

D1 prepared bindings prevent SQL injection. A unique `(player_id,event_id)` key plus a database trigger update the best score and accepted-game count atomically, so retries are safe. Ties favor the earlier received best. Basic plausibility checks reflect the plugin's unchanged 100/300/500/800 line scoring. Per-IP and per-player rate limits return 429 with Retry-After. These approximate limits do not replace a global abuse budget; the account should be monitored for unusual traffic. No raw IP/token/request body is written to application logs or D1.

## Privacy, removal and abuse

See the plugin's PRIVACY.md. A public nickname is pseudonymous, not a real-person identity. Tokens copied between computers share a profile; removing settings generates a new one. Do not promise anti-cheat or one-person-one-account guarantees: a modified open-source client can fabricate plausible scores and create multiple anonymous identities.

For removal, the player should disable Online ranking and discard pending results first. Technical users can authenticate a DELETE to their own `/v1/player` resource. The operator can resolve a contact request by exact nickname, verify ownership, and remove that player and its events through D1; never act on a nickname-only claim without checking ownership. Do not ask players to post tokens publicly. Provider backup retention also applies.
